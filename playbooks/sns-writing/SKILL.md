# 목적
출판용 도서 원고의 특정 목차 분량을 입력받아 브런치 전문 칼럼, 네이버 블로그 Q&A 글, 인스타그램 캡션, 스레드 본문·답글, GitHub 카드뉴스 자동 생성용 `current_post.json` 코드까지 5종 세트를 한 번에 작성한다.

# 언제 쓰는지
매주 월요일·금요일 정기 발행 시 내가 도서 원고의 특정 목차(절) 분량을 채팅창에 복사해 붙여넣거나 "SNS 원고 작성해 줘"라고 말할 때 실행한다.

# 입력
- 채팅창에 복사해 붙여넣은 도서 원고의 특정 목차(절) 본문 텍스트
- (선택) 이번 회차의 카드뉴스 테마 색상(`burgundy` / `deep_navy` / `forest_green`) 및 브런치 발행 글 번호

# 순서
1. 입력된 도서 원고에서 제목, 질문형 부제, 핵심 법리와 판례 번호, 실제 사례, 마지막 `[응급 처방 3줄 요약]`을 파악한다.
2. **1번 산출물 [브런치용 최종 원고]**를 작성한다.
   - 원본 원고 분량의 70% 이하로 압축하되, 전문성 있는 평어체(`~다`) 칼럼 형식으로 `[제목]`, `[부제]`, 도입부, 번호가 붙은 소제목 본문(1~5), 마무리 문단을 작성한다 (`심화 실무 노트 예고`는 넣지 않는다).
   - 본문 하단에 브런치 고정 안내 문구(브런치북 연재 및 출간 예정 안내, 칼럼 안내 및 무료 상담, 손해사정사 소비자선임권 안내)와 해시태그 15개를 한 줄에 하나씩 붙인다.
3. **2번 산출물 [네이버 블로그용 최종 원고]**를 작성한다.
   - 브런치 글과 검색 중복(유사문서)이 되지 않도록 문장 구조와 어미를 완전히 다르게 새로 쓴다.
   - 친절한 경어체(`~입니다/습니다`)를 사용하여 짧은 도입부(3~4문장) 뒤에 독자가 가장 궁금해할 핵심 질문 3가지(`Q1.` ~ `Q3.`)와 글머리 기호 답변 형식으로 구성한다.
   - 본문 하단에 블로그용 고정 안내 문구(`올바른 보상 문화를 위한 안내 및 무료 상담`, `[손해사정사 소비자선임권 활용 시 유의사항]`)와 해시태그 15개(가로 나열 1줄 + 세로 태그 목록)를 붙인다.
4. **3번 산출물 [인스타그램용 최종 원고]**를 작성한다.
   - 첫 줄에 `⚖️` 이모지와 함께 일상 속 흔한 질문 3가지를 큰따옴표로 던지고, 핵심 법리 3가지를 `✅`, `❌`, `✅` 이모지로 구분해 요약한다.
   - 하단에 무료 상담 및 소비자선임권 안내, 브런치 프로필 링크 유도 문구(`https://brunch.co.kr/@tl-oooooo`), 해시태그 11~15개를 붙인다.
5. **4번 산출물 [스레드(Threads)용 최종 원고]**를 작성한다.
   - `[스레드 본문 (main_text)]`: 구체적인 사례 질문과 직관적인 정답, 판례·법리 핵심 요약, 브런치 칼럼 유도 문구로 구성한다.
   - `[스레드 답글 (reply_text)]`: 무료 상담 및 소비자선임권 안내 문구와 핵심 해시태그 5개로 구성한다.
6. **5번 산출물 [GitHub `posts/current_post.json` 등록용 최종 코드]**를 작성한다.
   - `topic`, `theme_color`, `brunch_url`, `cards`(`slide1`, `slides_2_to_4` 3개 배열, `slide5`), `instagram.caption`, `threads.main_text`, `threads.reply_text`가 모두 포함된 완성형 JSON 코드 블록을 출력한다.
   - 내가 생성된 카드뉴스 이미지를 눈으로 확인해 네이버 블로그에도 함께 쓸 수 있도록 안내하고, 브런치 발행 후 글 번호를 `brunch_url`에 넣으라고 안내한다.

# 결정
- **채널이 브런치면** → 원고의 70% 이하로 압축하고 전문성 있는 평어체(`~다`)를 쓰며, `심화 실무 노트 예고` 섹션은 넣지 않는다.
- **채널이 네이버 블로그면** → 브런치와 유사문서로 묶이지 않게 어미만 바꾸지 말고 첫 문장부터 `Q1 ~ Q3` 문답형 구조와 친절한 경어체(`~입니다/습니다`)로 완전히 다르게 재작성한다.
- **카드뉴스 테마 색상(`theme_color`)을 지정할 때** → `burgundy`(버건디) → `deep_navy`(딥네이비) → `forest_green`(그린포레스트) 순서로 매 회차 돌아가며 적용한다. 내가 직전 색상을 알려주지 않았으면 어떤 색상 순서인지 확인하거나 지정된 순서에 맞춰 넣는다.
- **브런치 발행 전이라 글 번호를 모르면** → `current_post.json`의 `"brunch_url"` 값을 `"https://brunch.co.kr/@tl-oooooo/글번호입력"`으로 넣는다.
- **원고에 표나 약관 이미지가 있으면** → 이미지나 표를 그대로 복사하지 않고 핵심 기준과 수치만 텍스트와 글머리 기호로 풀어서 설명한다.
- **보험사나 소비자의 입장을 서술할 때** → 어느 한쪽 편만 들거나 과장된 광고성 표현을 쓰지 않고, 법령·판례·약관에 근거해 객관적이고 비평적인 전문가 시선을 유지한다.

# 완료의 정의
1. 5가지 산출물(① 브런치, ② 네이버 블로그, ③ 인스타그램, ④ 스레드 본문+답글, ⑤ `current_post.json` 코드)이 누락 없이 모두 출력되었는가?
2. 브런치 원고는 평어체(`~다`, 70% 이하 압축, 심화 노트 제외)이고, 네이버 블로그 원고는 경어체(`~입니다/습니다`, Q1~Q3 문답 구조)로 서로 문장이 겹치지 않게 분리되었는가?
3. 본문 내 판례 번호, 법조항, 숫자(금액·비율·기한)가 원고와 정확히 일치하며 임의로 지어낸 근거가 없는가?
4. 4개 채널 모두 하단 고정 안내 문구(무료 기초 상담 안내 + 자동차보험 등 감독규정 제외 대상을 명시한 손해사정사 소비자선임권 청구 전 상담 안내)와 해시태그가 빠짐없이 포함되었는가?
5. `current_post.json`의 카드뉴스 각 줄이 이미지 밖으로 넘치거나 글자 크기가 줄어들지 않도록 아래 글자 수 제한(공백 포함)을 엄격히 지켰는가?
   - `slide1`: `main_title` 15자 이내, `sub_title` 18자 이내, `left_caption` 각 줄 18자 이내(3줄)
   - `slides_2_to_4` 및 `slide5`: `title` 24자 이내, `headline` 25자 이내, `bullets`·`green_notes` 배열 및 `note` 문자열의 각 줄당 28자 이내
6. `current_post.json` 코드 안의 줄바꿈(`\n`)과 큰따옴표 이스케이프(`\"`)가 정상 처리되어 문법 오류 없는 유효한 JSON 형식인가?

# 예외 사례
- **카드뉴스 글자 넘침 및 폰트 크기 변형**: `current_post.json`에서 한 줄 글자 수가 길어지면 GitHub Actions(`scripts/generate_cards.py`) 실행 시 글자가 이미지 아래로 밀려 내려가거나 글자 크기가 어색하게 줄어든다. 파이썬 코드를 고치지 말고, JSON의 `bullets`와 `green_notes` 배열에서 한 줄이 공백 포함 28자를 넘지 않도록 문장을 두 줄(배열의 다음 문자열 요소)로 나누어 작성한다.
- **브런치·블로그 유사문서(중복 검색) 문제**: 브런치 문장의 어미만 `~다`에서 `~입니다`로 바꾸면 포털에서 중복 문서로 인식해 둘 중 하나만 노출된다. 반드시 블로그는 도입부 요약 + `Q1~Q3` 질문·답변 구조로 문단 구성 자체를 새로 짠다.
- **판례·법조항 왜곡 및 편향 서술**: 원고에 없는 판례나 법조항을 임의로 추가하거나 소비자를 현혹하는 과장 광고 멘트를 쓰면 안 된다.
- **고정 안내 문구 및 해시태그 누락**: 요약 과정에서 하단 무료 상담 안내, 소비자선임권 유의사항(자동차보험 제외 명시 및 접수 전 상담), 해시태그를 빠뜨리지 않도록 매회 고정 양식을 그대로 붙인다.
# 자동화 운영 기준
- 입력은 사용자가 지정한 PC 파일, Google Drive 파일, GitHub 파일 또는 채팅 원고에서 받는다. 실행 기록에 입력 위치와 사용 버전을 남긴다.
- 작업 등록 시 예상 소요 시간과 사용량 범위, 즉시 수행 부분과 새벽 대기 부분을 알리고 자동 진행한다. 사용자가 급하다고 지시하면 즉시 수행한다.
- 별도 API 과금은 허용하지 않는다. 구독 인증으로 실행 가능한 경로가 확인된 작업만 실제 모델에 전달한다. 한도 도달 시 진행 상태를 저장한다.
- 새벽 처리 기본 시간은 한국 시간 03:00~06:00이며 사용자 요청으로 조정한다. 월요일·금요일은 원고 준비 주기로 사용하며 실제 발행에는 사용자 승인이 필요하다.
- 배포, SNS 게시, 외부 발송은 결과물과 목적지를 사용자가 승인한 후 실행한다. 승인 후 내용이나 목적지가 바뀌면 다시 승인받는다.
- 공개 GitHub에는 미승인 원고, 도서 원문, 개인정보를 올리지 않는다. 자동화 코드와 검증용 가상 자료는 업로드 가능하다.

# 보완된 검증 기준
- 브런치 압축률은 공백 포함 본문 문자 수로 계산한다. 제목, 부제, 고정 안내, 해시태그를 원문과 결과 양쪽에서 제외하고 원문 문자 수, 결과 문자 수, 비율을 보고한다.
- JSON 파싱 성공, 필수 키, 중간 카드 3개, 카드별 문자 수, 채널별 해시태그 개수를 검사하고 실제 수치를 기록한다.
- 카드 이미지를 렌더링하여 잘림과 넘침을 확인한다. 렌더링하지 못했다면 미확인으로 표시한다.
- 고정 안내 문구 전문은 사용자가 제공한 브런치 41번 글에서 추출한 로컬 .runtime/notices.md를 사용한다. 전문이 없으면 임의 작성하지 않고 해당 검증을 대기로 표시한다.
- 원문과 법조항·판례·수치 대조 결과를 기록한다. 법적 정확성 검증이 필요한 경우 공식 원문과 대조하고, 확인 불가 항목은 미확인으로 표시한다.
- brunch_url의 글번호입력 또는 미확정 링크는 초안에서만 허용하고 게시 준비 검사에서 차단한다.
- posts/current_post.json 구조는 실제 scripts/generate_cards.py와 기존 정상 JSON을 대조한 후 호환성을 확정한다.
- 구조와 문장을 다르게 작성했는지 검토하되 검색 노출이나 유사문서 판정을 보장하지 않는다.
- 첫 검증에서 3개 이상 실패하면 실행을 멈추고 프로세스 원인을 보고한다.

# 오류 수정
- 오류 발생 시 프로세스, 툴박스, 증명 중 실패한 레이어와 이유를 먼저 두 문장으로 보고한다.
- 최소 수정 후 같은 입력으로 다시 검증하고 수정 전후 결과를 비교한다.
- notes.md 최신 항목에 날짜, 오류, 수정, 재검증 근거를 기록한다. 같은 오류가 반복되면 명시적 차단 규칙을 추가한다.

# 툴박스 연결
- files/output-schema.json의 응답 구조로 5종 결과를 작성한다. note는 문자열이다.
- scripts/sns-validator.mjs로 JSON 구조와 글자 수를 검사한다.
- 카드뉴스 색상 순서는 burgundy → deep_navy → forest_green으로 적용하고 기존 생성기의 색상 자동 변경에 의존하지 않는다.
